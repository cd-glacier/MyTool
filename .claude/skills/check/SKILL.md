# Check

このプロジェクトのルール群に沿った実装になっているかを確認するスキル。**指摘のみ**で修正はしない。

## 進め方

### 1. ルールを集める

以下を**全て**読み込む。存在しないものはスキップ。

- `~/.claude/CLAUDE.md`（グローバル）
- `<project>/CLAUDE.md`（プロジェクト、あれば）
- `<project>/CLAUDE.local.md`（あれば）
- `<project>/.claude/rules/` 配下の **全ての** `.md` ファイル（`ls` で列挙してから読む。今後ファイルが増えても自動的に対象になる）

ルール内容はこの SKILL.md にハードコードしない。**実ファイルを正**として扱う。SKILL.md の例示と食い違ったらルールファイル側を優先する。

### 2. 対象ファイルを決める

ユーザー指定がなければ変更ファイル。

```bash
git status --short
git diff --name-only
git diff --name-only --staged
git diff main...HEAD --name-only
```

範囲が曖昧（コミット済み変更まで含めるか等）なら一度確認する。

### 3. 各ルールを観点に変換してチェック

読み込んだルールから判定可能な観点を抽出し、対象ファイルに当てる。代表的な観点：

- **配置**: 各層のディレクトリ規約に沿った場所にファイルがあるか
- **命名**: クラス・ファイル名が命名規則に合致しているか
- **責務分離**: Screen が stateless か / ViewModel が Context 等に直接依存していないか / UseCase が Repository インターフェースに依存しているか など、各層の責務ルール
- **イミュータビリティ**: UiState / UiModel が `data class` + `val` か
- **API 形状**: Repository の `Flow` vs `suspend` 使い分け、UseCase の `operator fun invoke()` 単一公開など
- **環境制約**: Termux 前提（`./gradlew` を実行しない、`$PREFIX/bin` を使う、`pkg` を使う等）に反する手順・コードを混ぜていないか
- **コメント方針**: 不要なコメント・自明な docstring を追加していないか
- **言語**: 出力すべき文書（コミットメッセージ等）が日本語ルールに沿っているか
- **その他 rules/ に書かれた事項全般**

ルールに書かれていない好みの指摘はしない。

### 4. レポート

```
## チェック結果

参照ルール:
- ~/.claude/CLAUDE.md
- .claude/rules/architecture.md
- （他、読み込んだもの全て）

対象ファイル (<n>件):
- path/to/A.kt
- path/to/B.kt

### 違反
- `path/to/A.kt:42` — <ルール名/出典> に反する: <具体的な内容>
- ...

### 要確認 (グレー)
- `path/to/B.kt` — <理由>。意図的な可能性あり

### 問題なし
（書くこともあれば省略も可）
```

確実な違反のみ「違反」に入れ、判断が割れるものは「要確認」に分ける。誤指摘より控えめに。各指摘には**どのルールファイルのどの記述に基づくか**を必ず添える（ユーザーがルール側を更新するか実装側を直すかを判断できるよう）。

## 原則

- **指摘のみ**。修正コードは書かない。
- **ルールファイルが正**。SKILL.md と食い違ったらルール側を優先。SKILL.md の例示が古くなっていたら、その旨もレポート末尾に書く。
- ルールに無いことで指摘しない。
- 対象が広くなる場合は層ごと・ルールごとにグルーピングして読みやすくする。
